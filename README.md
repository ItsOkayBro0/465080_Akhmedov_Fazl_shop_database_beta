# Магазин — лабораторная по базам данных

Интернет-магазин из лекции №3: покупатели, товары, заказы и позиции заказов в
PostgreSQL. Приложение работает, но в нём три проблемы с базой данных: медленная
история заказов, продажа товара сверх остатка и дубли заказов при повторных
запросах. Их нужно исправить и подтвердить исправления измерениями и тестами.
Менять можно не только код, но и схему базы.

## Состав

```text
Браузер → Магазин (Bun, порт 3000) → PostgreSQL 18 (порт 5433)
```

- **Магазин** — API в `src/` и интерфейс в `public/`: каталог, корзина, «Мои
  заказы». Интерфейс считается корректным, его не меняйте.
- **PostgreSQL** — схема в `db/migrations/`. При первом запуске загружаются
  данные: 200 000 покупателей, 1000 товаров, 2 миллиона заказов и около
  5 миллионов позиций. База занимает около 550 МБ.

## Запуск

Нужен Docker:

```bash
docker compose up --build
```

Первый запуск генерирует данные, это 1–2 минуты. Когда в логе появится
`Магазин запущен`, откройте <http://localhost:3000>.

Код и миграции собираются в образ приложения. После изменений пересоберите его:

```bash
docker compose up -d --build app
```

Подключиться к базе:

```bash
docker compose exec db psql -U shop -d shop
```

Для тестов, линтера и скрипта одновременных заказов нужен
[Bun](https://bun.sh) 1.4 или новее:

```bash
bun install
bun run test     # тесты создают отдельную базу shop_test
bun run lint
bun run format   # исправить форматирование, если lint ругается на него
bun run race     # одновременные заказы: последний ноутбук и повтор запроса
```

Вернуть исходные данные: `docker compose down -v && docker compose up --build`.

```text
GET  /api/products?q=…  каталог, первые 24 товара
GET  /api/orders?page=N итоги покупателя и страница из 50 заказов с позициями
POST /api/orders        оформить заказ
```

```bash
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"items":[{"productId":2,"quantity":1}]}' \

```

## Миграции

Схема меняется только миграциями. При запуске `app` применяет новые файлы из
`db/migrations/` по порядку имён и записывает их в таблицу `schema_migrations`.
Уже применённые файлы не редактируйте, добавляйте новые: `002_….sql`,
`003_….sql`.

Данные загружаются в исходную схему `001_init.sql`, а ваши миграции применяются
уже к заполненной базе. Если миграция добавляет столбец, она должна заполнить
его и для существующих строк.

Каждый файл применяется в отдельной транзакции, поэтому
`CREATE INDEX CONCURRENTLY` в миграциях не работает. На этой базе обычный
`CREATE INDEX` строится за секунду.

## Что нужно исправить

### 1. История заказов открывается секундами

Раздел «Мои заказы» показывает заказы по 50 на странице и итоги покупателя за
всё время: сколько заказов и на какую сумму. Им пользуются и оптовые клиенты: у
ООО «Вектор» 40 000 заказов — это 800 страниц. Сейчас любая страница
открывается секунды, даже у покупателя с парой заказов, а с ростом базы будет
открываться ещё дольше. Время ответа видно над списком. Сделайте так, чтобы:

- запросы страниц истории, включая последнюю, шли по индексам и не читали
  таблицы целиком;
- число запросов к базе не зависело от числа заказов на странице;
- итоги не пересчитывались по всем позициям заказов при каждом открытии
  страницы, в том числе у «Вектора». Для этого можно менять схему — например,
  хранить сумму заказа в `orders.total`. Суммы должны быть верными и у старых,
  и у новых заказов.

### 2. Товар продаётся сверх остатка

Оформление заказа читает остаток, сравнивает его с количеством в коде и
записывает новое значение. Когда покупают одновременно, `bun run race` продаёт
несколько ноутбуков, хотя на складе был один. Сделайте так, чтобы:

- из одновременных покупок последнего товара проходила одна, а остальные
  получали `409`, а не `500`;
- заказ, его позиции и списание остатков сохранялись вместе или не сохранялись
  вовсе.

### 3. Повторный запрос создаёт второй заказ

Интерфейс отправляет с заказом заголовок `Idempotency-Key`. Если ответ не пришёл
и покупатель снова нажимает «Оформить заказ», запрос уходит с тем же ключом.
Сервер перед созданием ищет заказ с этим ключом, но одновременные повторы его не
находят: `bun run race` создаёт несколько заказов с одним ключом. Сделайте так,
чтобы:

- на один ключ создавался ровно один заказ даже при одновременных запросах, а
  гарантировало это ограничение в базе;
- повторные запросы получали тот же заказ, а не ошибку.

## Требования к решению

- Схема изменена только новыми миграциями.
- Для пунктов 2 и 3 добавлены тесты с одновременными запросами, которые падают на
  исходном коде. Исходные тесты не удалены и не ослаблены.
- Изменения точечные: без переписывания несвязанного кода.
- `bun run lint` и `bun run test` проходят, `bun run race` по обоим сценариям
  пишет `OK`.
